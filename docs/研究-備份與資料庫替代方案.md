# 研究：免費的備份存放地點 ＋ Supabase 的免費替代方案

> 2026-10-10 查證（Gary 指定：「備份要存到一個免費的地方（你幫我找）」、
> 「尋找可以完美替代 supabase 的免費方案（容量大，不限制同時只能有兩個）」）。
> **這份只是研究與規劃，還沒有動任何程式、沒有申請任何服務。**
> 所有數字都在 2026-10-10 當天從官方頁面查得；免費方案的規則會變，動工前要再看一次官網。

## 一、先講清楚現況（為什麼要備份、為什麼想搬家）

Supabase 免費方案（2026-10-10 官方 pricing／billing 文件）：

| 項目 | 免費方案 | 對我們的影響 |
|---|---|---|
| 資料庫大小 | 500 MB | 教學內容＋**錄音（base64 存在資料庫裡）**是主要用量 |
| Egress | 5 GB／月 | 學生查生字很省，通常夠 |
| 檔案儲存 | 1 GB | 我們沒在用 Supabase Storage（音檔在資料庫） |
| **同時專案數** | **2 個活躍專案**（限制看「你是 Owner／Admin 的所有組織」合計；暫停的不算） | Gary 目前：`gary-dictionary` ＋ 已暫停的「比賽管理系統」 |
| 閒置暫停 | **7 天沒有活動就暫停，要回後台手動還原** | 寒暑假期間網站會直接掛掉，直到有人去按還原 |
| **自動備份** | **完全沒有**（Pro $25/月起才有每日備份，而且不含 Storage 檔案） | ★ 這就是 A-2「唯一沒有退路的地方」 |

→ 所以有兩件事要規劃：**(1) 自己做備份**（不管資料庫留在哪，這都是必要的）；
**(2) 要不要搬家**（問題是「2 個專案上限」＋「閒置暫停」＋「沒有備份」）。

## 二、免費的備份存放地點（候選比較）

| 地點 | 免費容量 | 自動化 | 要新帳號／信用卡？ | 私有？ | 從哪裡跑 |
|---|---|---|---|---|---|
| **Cloudflare R2** | 10 GB-month／月；**egress 完全免費**；S3 相容 API | ★ 最好（Vercel 函式可直接寫） | 要 Cloudflare 帳號；**建立 bucket 前可能要求付款方式** | ✅ | 伺服器端（不需要你的 Mac 開著） |
| **私有 GitHub repo** | 免費私有 repo 無限；Releases 每個檔案 < 2 GiB、單一 release 沒有總容量上限 | ★ 好（我們已經有 token） | 不用（**已有的 GitHub 帳號**） | ✅（但**要另開一個私有 repo**，目前這個 repo 是公開的） | 伺服器端或你的 Mac |
| **Google Drive** | 15 GB（與 Gmail／相簿共用） | 好（這台 Mac **已經授權** Drive 權限） | 不用（你的 Google 帳號） | ✅ | 你的 Mac（要醒著；可用 launchd 開機後補跑） |
| **Backblaze B2** | 前 10 GB 永久免費；S3 相容；每天免費 egress＝3× 平均儲存量 | 好 | 要 B2 帳號（部分流程會要求付款資訊，要實測） | ✅ | 伺服器端或你的 Mac |
| Supabase Storage | 1 GB | 可 | 不用（現有帳號） | ✅ | ✗ **不建議當唯一備份**：跟資料庫同一個服務，服務出事時一起消失 |
| Storj | 目前主打 30 天免費試用，免費方案資訊不明確 | — | — | — | 先不考慮 |

### 我的建議（三層，免費）

1. **主要備份：Cloudflare R2**（10 GB、免 egress）＋用 **Vercel Cron** 每天在伺服器端跑一次。
   Vercel **Hobby 方案**每天可以跑一次 cron（Hobby 限制：**每天一次**、時間精度 ±59 分鐘；Pro 才能每分鐘）。
   → 好處：**不需要你的 Mac 開著**、不用手動、失敗會留紀錄。
2. **如果你不想填付款方式**：改用一個**私有 GitHub repo**（`gary-dictionary-backup`）每天 commit 一份 dump。
   零新帳號、零費用、我們已經有可寫入的 token；缺點是 GitHub 不建議把 repo 當通用備份服務（我們每份 dump 只有幾 MB，很安全）。
3. **第二份異地（每月一次）**：Mac 上的腳本把最新 dump 上傳到 **Google Drive**（15 GB、已授權）。
   兩個地方都有 = 一個服務掛掉還有一份。

### 備份內容與還原（不管存哪裡都一樣）

- 內容：7 張表全部（`books`／`units`／`entries`／`users`／`grants`／`audio`／`audit_logs`）＋錯誤日誌。
  ★ **音檔要單獨抓**：列表查詢刻意不含 base64（`HEAVY_FIELDS`），備份要用單筆端點把 `audio_data` 一起帶走。
- 每份 dump 是**一個 JSON 檔**（外加 manifest：時間、版本、筆數、雜湊），命名 `gary-dictionary-YYYY-MM-DD.json`。
- 保留策略：每天一份保留 14 天、每月一份保留 12 個月（在備份端刪舊的，不是刪來源）。
- 還原：`scripts/restore.js --file <dump> --dry-run` 先預覽筆數 → 真的還原時**只 upsert、永不刪除**；
  還原後跑 `npm run check:schema:live` ＋ `live-verify`；**每月實測還原一次到臨時資料庫**（沒實測過的備份不算備份）。
- **需要你決定**：① 存哪裡（R2／私有 GitHub repo／兩者）② 要不要每天自動 ③ 接不接受為 R2 填一次付款方式。

## 三、Supabase 的免費替代方案

需求：**容量大**、**沒有限制同時只能兩個專案**、對我們的程式改動越小越好。
我們的資料層（`lib/store/supabase.js`）只用到 **PostgREST 風格的 REST**（`/rest/v1/<table>?...`）＋service role key 繞過 RLS，
所以「相容性」＝**有沒有現成的 PostgREST 相容 REST**。

### 候選比較

| 方案 | 免費容量 | 專案數 | 與我們的相容性 | 遷移工作量 | 風險／備註 |
|---|---|---|---|---|---|
| **Neon ← 首選** | **1 GB／專案**（全部專案合計 20 GB）、5 GB 對外流量／專案／月、100 CU-hours／專案／月（可到 2 CU ≈ 8 GB RAM） | **100 個專案**、每專案 10 個分支 | ★ **有 PostgREST 相容的 Data API**（新的 Rust 實作）；官方還發了 **Supabase 完整遷移指南** | 中：授權從「service role key 繞過 RLS」改成「JWT＋GRANT／RLS」；查詢語法基本一樣 | 有 **新加坡 `aws-ap-southeast-1`**（跟現在同區，Vercel 函式在 sin1）；閒置 5 分鐘 scale-to-zero，但**下一個請求會自動喚醒**（不像 Supabase 要手動還原）；Instant restore 只保留 6 小時 |
| **第二個 Supabase 帳號** | 同免費方案（500 MB／專案） | 每帳號 2 個專案 | 100% 相容（**零改程式**） | 小（換環境變數） | 只是繞過「2 個專案」限制；500 MB、7 天閒置暫停、沒有自動備份的問題**都還在** |
| Xata | **15 GB**（單一團隊成員、10 分支） | 多 | ✗ 自己的 REST API（不是 PostgREST）；Postgres 存取還在 beta（限制語句、不能用 extension） | 大（要改寫資料層） | 好處：不停機、不冷啟動 |
| 自架 Supabase（Oracle Cloud Always Free） | 免費額度：2× AMD micro VM（1 OCPU／1 GB）＋ Ampere A1 每月 **1,500 OCPU-hours ＋ 9,000 GB-hours**（≈ 2 OCPU＋12 GB 可 24×7 跑；4 OCPU／24 GB 只夠半個月）＋ 200 GB 區塊儲存 | 自己的機器，無限 | 100% 相容（就是 Supabase） | 大（Linux／Docker 運維、TLS、備份、升級、監控全要自己做） | 免費額度會變動、熱門區常「沒有容量」可開；掛掉要你自己救 |
| Cloudflare D1 | 每個 DB 500 MB、每帳號 10 個 DB、合計 5 GB | 10 | ✗（SQLite，要自己寫一層 API） | 大 | 有 7 天 Time Travel（點時還原） |
| Turso | 5 GB、**DB 數不限**、每月 500M rows read／10M written | 不限 | ✗（SQLite over HTTP） | 大 | 需要改 SQL 方言 |
| CockroachDB Basic | 每月 $15 免費額度 ≈ 10 GiB 儲存＋50M RU | 額度制 | ✗ 沒有 PostgREST | 大 | 對我們的規模太重 |

### 我的建議

1. **先不要搬家。** 現在的痛點是「沒有備份」而不是「不夠用」（實際用量：1 本書／1 單元／1 生字）。
   先把 A-2 備份做起來，容量問題用 D-6（月檢＋提醒）盯著。
2. **搬家第一順位是 Neon**：100 個專案、1 GB／專案（合計 20 GB）、同一區（新加坡）、
   PostgREST 相容（我們的 `lib/store/supabase.js` 改動最小）、而且**閒置自動喚醒**（比 Supabase 免費的「手動還原」適合校園使用）。
3. **動手前先做「影子驗證」**（不碰現有資料）：開一個免費 Neon 專案 → 套同一份 `migrations/` →
   把 `SUPABASE_URL`／金鑰指向它跑 `live-verify` 與 `check:schema:live` → 量冷啟動延遲與寫入行為。
   通過才談正式搬家（正式搬家還要處理：現有資料匯出／匯入、JWT／RLS 授權模型、稽核與備份腳本改寫）。
4. **最省事的備案**：真的只是要「突破 2 個專案」→ 開第二個 Supabase 帳號就好，零改動。

### 要你決定／要你做的事

- 要不要我**現在**開一個免費 Neon 專案做影子驗證？（需要你用 email 註冊 Neon；我不會碰你現有的 Supabase 資料）
- 還是先只做備份，搬家等真的遇到容量問題再說？
- 提醒：Supabase 免費專案**7 天沒活動會暫停**（要手動還原）。如果某個長假網站會停，這是比容量更該先解的問題
  （解法：換 Neon，或加一個「每天叫一次」的 keep-alive——但 keep-alive 會用掉 egress，且違反平台善意使用的精神，不建議）。
