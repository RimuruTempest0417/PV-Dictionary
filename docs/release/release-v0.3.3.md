## PV_Dictionary v0.3.3 — 載入速度（實測 3.9 秒 → 0.3 秒）＋ 載入動畫

你的原話：「現在每個頁面的載入速度都很慢，然後在載入途中加一個 Loading 的動畫」。

### 慢在哪（先量，再改）

| 端點（production，改之前） | 第一次 | 第二次 | 第三次 |
|---|---|---|---|
| `/`（HTML） | 1.01s | 0.29s | 0.31s |
| `/api/version` | **5.49s** | 2.79s | 2.85s |
| `/api/health` | 2.74s | 2.21s | 3.13s |
| `/api/books` | 2.20s | 2.66s | 2.23s |

三個原因疊在一起：

1. **每個 `/api` 請求都把 7 張表整份抓一次**（v0.3.2 為了「別的實例寫的資料要馬上看到」改成 ttl=0）。
   連 `/api/version` 這種不需要資料庫的端點也在等 7 個查詢。
2. **每次都 `select=*`**：書本封面（每本 2MB base64）與老師錄音（每段 1MB base64）全部跟著抓下來 ——
   就算只是要一份書名清單。老師錄 10 段音之後，這會直接變成幾十 MB 的傳輸。
3. **Vercel 函式跑在 `iad1`（美東），資料庫在 `ap-southeast-1`（新加坡）**：每一趟查詢都要飛半個地球。

### 改了什麼

| 改動 | 效果 |
|---|---|
| 資料層加 **ttl 快取（預設 3 秒）**，自己寫入成功後立刻把快取視為最新 | 一次頁面載入打好幾支 API，只有第一支真的查資料庫；其餘 1ms 內回 |
| **大欄位（封面／錄音 base64）不進快取**，`GET /api/covers/:id`、`/api/audio/:id` 才單筆抓 | 一般請求不再搬 MB 級的 base64；`has_cover` 改看 `cover_bytes` |
| **不需要資料庫的路由直接放行**（`/api/version`） | 5.49s → **5ms** |
| **Vercel 函式區搬到 `sin1`（新加坡）**，和資料庫同區 | 每趟查詢延遲從 ~250ms 降到 ~5ms |
| 靜態檔 `max-age=7d` ＋ 所有 CSS/JS/圖示帶 `?v=<版本>`（HTML 維持 no-cache） | 回訪不用重新下載、改版自動換網址 |

本機（連同一個線上資料庫）實測：`/api/version` 5ms、第一次 `/api/books` 333ms（要抓 7 張表）、
**同一秒內後續請求 1ms**。線上（sin1）數字見下面「實測」。

### 載入動畫

- **頂部進度條**（`#appLoader`，3px，accent 色）：任何 API 還在飛就顯示，
  由 `public/js/api.js` 統一開關（`ui.js` 的 `PDLoader` 負責計數與「最短顯示 350ms」——
  太快閃一下反而像畫面壞掉）。
- **書架骨架屏**（`#shelfSkeleton`）：第一次載入書架時先放 3 張佔位卡，不再是空白畫面。
- 只動 `transform` / `opacity`，並且 `prefers-reduced-motion: reduce` 時全部改成靜態；
  進度條帶 `role="status"` ＋ 螢幕閱讀器文字（`a11y.loading`，中英都有）。

### 還會影響速度的兩件事（下一步可以考慮）

1. 資料層仍是「整表讀進記憶體、回應前寫回」的模型：**資料量再大（幾千個生字）就會開始有感**，
   那時候要改成只查需要的列（伺服器端分頁）與資料庫層的交易。
2. `/api/books` 一次就把所有書＋單元算好（現在很好，但書很多時要改成兩段式載入）。
