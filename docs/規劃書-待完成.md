### D-10（P2）權限模型的小矛盾：被授權的學生編得動，但前端說不行
- **為什麼**：後端 `lib/roles.js` 的 `canEditUnit()` 只要「有 `can_edit` 授權」就允許編輯（不分角色），
  但 `lib/capabilities.js`（權限唯一來源）宣告 `can_edit` 需要 class_rep 以上 →
  前端對學生回 `can_edit:false`（按鈕藏起來）。結果是**兩邊說法不一致**：學生若直接打 API 其實編得動
  （2026-10-10 安全審查發現；README 寫的是「被授權的人可以加入生字」，所以這可能是刻意的）。
- **怎麼做**：二選一 —— ① 建立授權時限制「`can_edit` 只能給 class_rep 以上」；
  ② 或讓 capabilities 承認授權（有授權就有 `can_edit`，前端也照這個顯示）。
  要照實際教學流程決定（誰會被授權）。
- **工作量**：小（一行＋守門測試）。

### D-11（P1）資料層：把分頁與搜尋下推到資料庫（**已知的規模天花板**）
- **為什麼**（2026-10-10 實測）：在**同一個單元塞 10,000 個生字**時：
  單元第一頁 **2,575 ms**、深頁 2,533 ms、搜尋 2,705 ms（1 個生字時是 105 ms），
  24 條併發下 **1,096 個請求有 1,077 個回 503**，連刪除測試資料都讓 Neon 回
  `53200 out of memory`。同一時間用**輕查詢**測 30 條併發是 **100% 成功、零 503**
  （Neon 直連 p50 66 ms、正式站 p50 93–260 ms）→ 問題不在併發，而在**每個請求都把整個單元的生字搬進記憶體**。
- **怎麼做**：生字表的讀取改成「資料庫端分頁」——`/api/units/:id` 用 PostgREST 的
  `limit`／`offset`／`order` 加上 `Prefer: count=exact` 取一頁，搜尋用 `ilike`（搭配 `headword_norm` 索引），
  單元詳情只回那一頁。這是 v0.6.1（D-1b「視窗化」）剩下的一半：當時只做到「只抓這一條請求要用的切片」，
  但一個單元的切片還是整個單元。
- **收穫**：一萬個生字的單元也能維持百毫秒級；免費方案的 0.25 CU 不會被單一請求打爆。
- **工作量**：中（改 `lib/store/supabase.js` 的視窗與 `server.js` 的單元路由＋假 PostgREST 的查詢形狀＋效能守門）。
- **現況註記**：現在的資料量（1 書／1 單元／1 生字）完全不受影響，所以不急；
  但這是「老師把整本生字貼進一個單元」時會撞到的天花板，要排在功能之前。

## 刻意不做的事

- 公開自助註冊與邀請碼：校內使用，帳號一律由管理員建立（學生免登入即可查）。
- 推播通知（Web Push／VAPID）：老師人數少、站內顯示足夠；iOS 還要「加到主畫面」才收得到。
- QR 掃碼、候補名額、成績排名：那是比賽管理系統的核心，不是字典。
- 對外 API／跨網域存取：所有請求同源，維持嚴格 CORS。
- 為了容量付費升級資料庫：目前 9.84 MB / 1 GB（1%），先用「每單元錄音上限＋用量顯示＋70% 警告」管理。
  真的不夠時：先評估 Neon 付費或第二個免費專案，最後才考慮自架。
- **自架 Supabase on Oracle Always Free**：使用者 2026-10-10 指定留到後期。評估已完成（`docs/研究-Oracle自架評估.md`），
  結論是**現在不要做** —— 官方 2026-06 把免費額度從 4 OCPU／24 GB 砍成 **2 OCPU／12 GB** 且沒有公告、
  閒置 7 天可能被回收、維運（OS／Postgres／TLS／備份／升級）全要自己來。重啟條件寫在那份文件裡。

## 工作方式

- **每一版做完停下來等確認**，使用者說「繼續」或「好」才做下一版。
- **版本號維持 `0.x.x`**；要跳 `1.x.x` 只有使用者說了才改。
- 發版條件（全綠才發）：`npm run check`（語法＋schema＋測試）／`npm run check:browser`（本機真 Chrome）／
  `npm run check:live-browser`（正式站真瀏覽器）／`live-verify`／`uptime`。
- 線上驗收一律用臨時帳號與 id 水線，結束後清乾淨並比對「筆數回到開始前」。
- **檢查可以截圖，但用完就刪**（不留在專案或使用者的電腦）；回報以純文字＋實測數字為主。
  （專案機制：`screenshot()` 預設不寫檔。）
- 機密（`JWT_SECRET`、資料庫金鑰、`VERCEL_TOKEN`、Neon 私鑰）只在 `.env → 雲端` 之間流動，**不經對話**。
- 資料庫變更一律寫進 `migrations/`；切換後端／回滾用 `node scripts/switch-backend.js`（見 `docs/搬家到Neon.md`）。
