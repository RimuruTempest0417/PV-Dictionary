### v0.7.0 — 聚合函式 ＋ 容量月檢（**下一個對話直接開始實作**）

**你要做的只有兩件**：① 把下面那段 SQL 貼到 Supabase → SQL Editor → Run（約 1 分鐘）
② 決定容量警告門檻（我建議 70%，留時間清資料）。

```sql
-- v0.7.0（D-1c ＋ D-6）：一次貼上、一次執行
-- 1) 每個單元有幾個生字（取代現在抓 unit_id,status 兩欄回來自己算）
create or replace function public.dict_entry_counts(unit_ids bigint[])
returns table (unit_id bigint, status text, n integer)
language sql
stable
as $$
    select e.unit_id, e.status, count(*)::int as n
    from public.dict_entries e
    where unit_ids is null or e.unit_id = any(unit_ids)
    group by e.unit_id, e.status;
$$;

-- 2) 資料庫真正的大小（D-6 的用量百分比；不用估）
create or replace function public.dict_db_size()
returns bigint
language sql
stable
as $$
    select pg_database_size(current_database())::bigint;
$$;

-- 3) 只給 service_role（我們的伺服器就是用這把；anon／authenticated 一律拒絕）
revoke all on function public.dict_entry_counts(bigint[]) from public, anon, authenticated;
revoke all on function public.dict_db_size() from public, anon, authenticated;
grant execute on function public.dict_entry_counts(bigint[]) to service_role;
grant execute on function public.dict_db_size() to service_role;

-- 4) 讓 PostgREST 立刻看到新函式（不然要等它自己重載快取）
notify pgrst, 'reload schema';
```

**實作順序（下一個對話照這個走）**
1. 先等你跑完 SQL；我用 `POST /rest/v1/rpc/dict_db_size` 讀回確認函式真的存在（404 就是還沒建好）。
2. `lib/store/supabase.js` 的 `prefetch()`：`entries?select=unit_id,status&limit=100000`
   → `POST /rest/v1/rpc/dict_entry_counts`（body `{ unit_ids: [...] }`），回傳形狀維持 `{unit_id,status,n}` 不變。
3. `lib/store/json.js` 不改（對外介面相同）；`countEntries()`／`requireCounts()` 不動。
4. 假 PostgREST（`tests/supabase.test.js`）要支援 `/rest/v1/rpc/*`；加回歸測試
   「prefetch 不再出現 `select=unit_id,status`」。
5. `scripts/schema-check.js`：加「線上兩個函式都存在」的檢查（空陣列試打 rpc，用回應分辨 404／400）。
6. D-6：`/api/health` 的 `db.usage`（bytes／percent／quota）＋管理區「📊 概況」顯示百分比
   ＋ `npm run uptime` 與 `npm run db:usage` 超過門檻回非 0（門檻常數只在一處定義）；
   `docs/監控與錯誤追查.md` 寫明「到門檻要做什麼」。
7. 驗收：`check:syntax`／`npm test`／`check:browser`／`live-verify --ephemeral-teacher`／
   `check:live-browser`／`uptime`／`check:schema:live` ＋ `npm run perf:entries` 前後比較（回應大小／時間）。
8. 發 v0.7.0（commit → tag → push → `gh-release` → 獨立讀回），完成後停下來等你檢閱。

       一次輸出一個 JSON（7 張表＋錯誤日誌＋manifest：時間／版本／筆數／雜湊）。
       ★ **音檔要單獨抓**：列表查詢刻意不含 base64（`HEAVY_FIELDS`），備份要用單筆端點把 `audio_data` 一起帶走。
    2. **存放（★ 你 2026-10-10 決定：放「私有 GitHub repo」）**：另外開一個**私有** repo
       （名稱暫定 `gary-dictionary-backup`），每天用現有的 GitHub token 推一份 dump ——
       GitHub 的 Releases 單檔 < 2 GiB、**單一 release 總大小與流量無上限**，我們每份只有幾 MB，非常安全。
       （研究過的其他選項：Cloudflare R2 10GB＋egress 免費、可完全在伺服器端跑；Google Drive 15GB 已授權；
       Backblaze B2 前 10GB 免費 —— 這些先留著，需要異地第二份時再說。）
       保留：每日 14 份、每月 12 份。
    3. **還原**：`scripts/restore.js --file <dump>` 一律 **upsert、永不刪除**、先 `--dry-run` 預覽筆數；
       還原後跑 `check:schema:live` ＋ `live-verify`；**每月實測還原一次到臨時位置**（沒實測過的備份不算備份）；
       補一份「怎麼還原」的文件（含「動手前先備份當下快照」的規矩）。
  - 工作量：中。**需要你決定**：① 備份放哪裡（R2／私有 GitHub repo／兩者）② 要不要每天自動跑。

## 刻意不做的事

- 公開自助註冊與邀請碼：校內使用，帳號一律由管理員建立（學生免登入即可查）。
- 推播通知（Web Push／VAPID）：老師人數少、站內顯示足夠；iOS 還要「加到主畫面」才收得到。
- QR 掃碼、候補名額、成績排名：那是比賽管理系統的核心。
- 對外 API／跨網域存取：所有請求同源，維持嚴格 CORS。
- 為了容量付費升級 Supabase：v0.6.0 決定維持免費方案，改用「每單元錄音上限＋用量顯示」管理。

## 工作方式

- 每一版做完停下來等你確認，你說「繼續」或「好」才做下一版。
- 發版條件（全綠才發）：`npm run check`（語法＋schema＋測試）／`npm run check:browser`（本機真 Chrome）
  ／`npm run check:live-browser`（正式站真瀏覽器）／`live-verify`／`uptime`。
- 線上驗收一律用臨時帳號與 id 水線，結束後清乾淨並比對「筆數回到開始前」。
- 檢查可以截圖，但**用完就刪**（不會留在專案或使用者的電腦）。
