# 研究：在 Oracle Cloud Always Free 自架（值不值得）

> 寫於 2026-10-10（v0.10.0 之後）。這是使用者指定「留到後期、有更進一步需求時再評估」的那一項，
> 先把它查清楚、把數字記下來，需要時才不用重新研究。
> 相關：`docs/研究-備份與資料庫替代方案.md`（各家免費方案比較）、`docs/搬家到Neon.md`（目前的做法）。

## 0. 結論（先講）

**現在不要做。** 技術上可行，但「免費」的代價是**維運全包**，而 Oracl​e 的免費額度**已經被砍過一次且不通知**。
目前（1 書／1 單元／1 生字、資料庫 9.84 MB）用 Neon 免費方案綽綽有餘，而且我們有每日備份到私有 repo。
**重啟評估的條件**（任一）：① 資料庫用量超過 1 GB 的 70%（=716 MB，`npm run uptime` 會叫）
② 真的放進大量錄音、需要超過 1 GB ③ Neon 的 Data API 結束 Beta 時改變規則或收費。

## 1. 官方免費額度（2026-10-10 查證，取自 Oracle 官方 Always Free 文件）

| 項目 | 額度 |
|---|---|
| Ampere A1（Arm）運算 | **2 OCPU ＋ 12 GB 記憶體**（彈性分配，可拆成兩台；**24×7 都在額度內**） |
| AMD 微型 VM | 2 台（1/8 OCPU、1 GB 記憶體）|
| 區塊儲存 | **200 GB**（開機磁碟＋區塊磁碟合計，只能在 home region）＋ 5 個磁碟備份 |
| 物件儲存 | 20 GB |
| 對外流量 | **10 TB／月** |
| 自治式資料庫 | 20 GB（跟我們無關，但它是「真的免費資料庫」的另一條路） |

**★ 兩件一定要知道的事**

1. **額度被砍過，而且沒有公告**：2026-06-15 官方把 A1 從 4 OCPU／24 GB 砍成 **2 OCPU／12 GB**
   （官方文件兩處至今仍不一致：一處寫 3,000 OCPU 小時／4 OCPU、另一處寫 1,500／2 OCPU），
   並自 **2026-08-18** 起終止超出新額度的既有免費執行個體。**任何寫 4 OCPU／24 GB 的文章都已經過時。**
2. **閒置會被回收**：7 天內同時滿足「CPU 95 百分位 < 20%」「網路 < 20%」「記憶體 < 20%（A1 才有看記憶體）」
   就會被判定閒置、**可能被 Oracle 回收**。我們這種低流量網站**正好符合閒置特徵**。
   另外常見的還有「Out of host capacity」——免費 Arm 主機在熱門區域常常開不起來。

## 2. 自架 Supabase 要面對什麼

同一個官方免費額度也可以改跑 **PostgREST**（我們現用的相容層）或 Supabase 自架包，好處是 200 GB 儲存、
不再依賴 Beta 的 Data API；代價是：

| 項目 | 實情 |
|---|---|
| 記憶體 | 官方最低 **4 GB**、建議 8 GB；一整包（Postgres＋PostgREST＋Studio＋Realtime＋Storage＋Pooler…約 11 個容器）**閒置就要 2.5–3 GB**。12 GB 夠用但沒有餘裕 |
| CPU | 2 OCPU 要同時養 Postgres 與十幾個容器 → 小流量可以，尖峰（多人同時上傳錄音）會吃緊 |
| 磁碟 | 40 GB 起跳（我們 200 GB 夠），但**資料庫＋WAL＋備份都在同一顆磁碟**，要自己搬去別處 |
| TLS／網域 | 要自己簽憑證（Caddy／Let's Encrypt）並自動續期 |
| 備份 | 官方自架**沒有** managed backup／PITR → 要自己排程 `pg_dumpall`、加密、傳到別的地方（我們現有的私有 repo 流程可以沿用） |
| 升級 | OS 與 Postgres 的安全性更新、Supabase 版本升級（compose 可能跳 Postgres 大版）都要自己看、自己承擔 |
| 監控 | 我們現有的 `npm run uptime` 可以打自己的服務；但「主機本身掛掉」需要另一套（Oracle 內建監控有免費額度） |
| 建置工作量 | 從零到穩：**大**（一次 1–2 天，之後每月固定維運時間） |

## 3. 對照：現在的做法（Neon Data API）

| 面向 | Neon（現在） | Oracle 自架 |
|---|---|---|
| 容量 | 1 GB | 200 GB |
| 費用 | 0 | 0（但**要付出維運時間**，且額度隨時可能被改） |
| 維運 | 0（平台負責） | 全部自己來 |
| 閒置 | 5 分鐘休眠、自動喚醒（實測喚醒 +1 秒） | 閒置 7 天可能被**回收** |
| 備份 | 我們自己推到私有 repo（每天自動） | 也要自己做（同一套可沿用） |
| 風險 | Data API 是 **Open Beta** | 平台政策風險（已發生一次砍額度）＋主機掛掉要自己救 |

## 4. 如果哪天真要做，順序建議

1. **先擴容量而不是先搬家**：Neon 付費或第二個免費專案（100 個專案可用）都比自架便宜（時間成本）。
2. 真的要自架時：`docker compose`（**只留 Postgres ＋ PostgREST**，砍掉 Studio／Realtime／Storage／Edge 等用不到的服務，
   把 3 GB 閒置降到 1 GB 以下）＋ Caddy（HTTPS）＋ 每日 `pg_dumpall` 到既有備份 repo ＋ `uptime` 監控。
3. **讓主機不要被判閒置**：在額度允許下保留一個小工作負載（例如每分鐘的健康檢查自己打自己），
   並接受「Oracle 隨時可能調整免費政策」這個前提——所以**正式資料仍然要有异地備份**（我們已經有了）。
4. 一定要先寫好**回滾**：資料庫在雲上，切回去的成本比 API 相容層低（同一套 PostgREST 語法），這是選它的最大優點。
