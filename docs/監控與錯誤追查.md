# 監控、錯誤追查與保留政策（v0.4.2）

這一頁回答三個問題：**壞掉了怎麼知道？壞掉了怎麼查？資料會不會滿？**

---

## 1. 壞掉了怎麼知道（D-4）

### 外部監控（免費，設定一次就好）

用任何支援「HTTP 檢查」的免費服務（例如 UptimeRobot、Better Stack、Healthchecks.io 的免費方案），
設定步驟都一樣：

1. 新增一個 **HTTP(s) monitor**。
2. 網址填：`https://pv-dictionary-mylearning.vercel.app/api/health`
3. 檢查間隔：**5 分鐘**（免費方案通常最短就是這個）。
4. 判斷條件選 **「回應內容包含」**，填 `"schema_ready":true`（這樣連「網站活著但資料庫掛掉」也抓得到）。
5. 通知方式填你的電郵或手機 App 推播。

> 為什麼用 `/api/health` 而不是首頁：首頁在資料庫壞掉時**還是會回 200**（HTML 是靜態檔），
> `/api/health` 會回 `schema_ready`、`db.ok`、`counts`，才是真的「能不能用」。

### 手動／排程檢查

```bash
npm run uptime                  # 檢查版本、健康（含資料庫）、公開讀取、首頁；有任何一項失敗就 exit 1
npm run uptime -- --json        # 給排程或監控讀的機器可讀輸出
```

要放進 Hermes 的排程（每天早上檢查一次，失敗就通知你）：用 `cronjob_manage` 建一個每天跑
`cd <專案> && npm run uptime` 的工作即可；它失敗時 exit code 會是 1。

## 2. 壞掉了怎麼查（A-5）

### 後台「🐞 錯誤紀錄」

登入（`admin` 以上）→「✏️ 管理」→「🐞 錯誤紀錄」。這裡會自動出現兩種紀錄：

| 來源 | 什麼時候寫入 | 例子 |
|---|---|---|
| 瀏覽器（`client`） | 前端發生未被捕捉的例外、未處理的 Promise 失敗、CSP 擋掉東西、資源載入失敗 | 老師說「按下去沒反應」時的那個錯誤 |
| 伺服器（`server`） | 後端回應 500、資料庫連不上（`DB_UNAVAILABLE`） | 上傳封面時資料庫說欄位不存在 |

每一筆都有：時間、等級（error／warn）、來源、錯誤碼、訊息、頁面路徑、版本。
**不保存截圖、不保存任何個資**（只有瀏覽器版本與路徑；網址不含查詢參數，避免把權杖外流）。

- 修好之後按 **「標記已處理」**（會留一筆稽核 `ERROR_LOG_UPDATE`），列表上方會顯示還有幾筆未處理。
- 篩選：等級、來源、狀態（未處理／已處理）、日期區間。
- 前端有節制：同一個錯誤 30 秒內只送一次、每次載入最多 10 筆、已知的無聲噪音（TTS 被中斷、
  `ResizeObserver`、跨來源 `Script error`）不送；401／403／404 這種「使用者按錯」不送（那是稽核的事），
  5xx 一定送。後端端點本身有節流（同一來源每分鐘 20 次）。

### 定期巡檢

```bash
npm run triage                  # 只列未處理，依出現次數排序（唯讀，不會改任何資料）
npm run triage -- --all         # 連已處理的一起看
npm run triage -- --days=7      # 只看最近 7 天
```

> ★ 看**線上**的錯誤日誌要指定資料層，否則它會讀你本機的檔案（本機預設是 JSON）：
> ```bash
> DATA_BACKEND=supabase npm run triage -- --days=7
> ```
> 同理 `npm run usage`、`npm run cleanup:logs` 也是一樣（它們都跟其他工具吃同一個 `DATA_BACKEND`）。

輸出會把同樣的錯誤分組：「出現 42 次（未處理 42）」——先修這一種就對了。

### 為什麼稽核紀錄裡看不到自動化檢查的動作（E-4）

驗收腳本（`npm run uptime`、`scripts/live-verify.js`…）跑一輪會在稽核紀錄留下十幾筆動作。
它們帶著用 `JWT_SECRET` 簽的 `X-PV-Self-Test` 標頭，伺服器驗簽通過就標成 `is_self_test`，
**稽核紀錄預設把它們濾掉**（想看就帶 `hide_self_test=0`，或取消該篩選）。
簽章不對、過期、或沒帶 → 一律當成真人操作（絕不因為標頭就放行任何權限）。

## 3. 資料會不會滿（D-5）

### 用量

```bash
npm run usage                   # 各表筆數（本機 JSON 或線上 Supabase 都自動判斷）
npm run usage -- --json
```

超過提醒門檻（稽核 5000 筆／錯誤日誌 2000 筆）就會在最後提醒你該清理了。

### 清理（預設只預覽，不會刪）

```bash
npm run cleanup:logs                       # 預覽：錯誤日誌 90 天、稽核 365 天
npm run cleanup:logs -- --apply             # 真的刪
npm run cleanup:logs -- --error-days=60 --audit-days=180
npm run cleanup:logs -- --only=error        # 只處理錯誤日誌
```

規則（刻意保守）：

- **錯誤日誌**：只刪「已標記處理」且超過天數的；**未處理的永遠留著**。
- **稽核紀錄**：超過天數就刪（稽核是「誰做了什麼」，留得比錯誤日誌久：預設 365 天）。
- 天數下限 30 天，避免手滑清掉一個月內的紀錄。

### 建議節奏

| 頻率 | 做什麼 |
|---|---|
| 每週 | 開後台看「🐞 錯誤紀錄」，把未處理的清一清（或 `npm run triage`） |
| 每月 | `npm run usage` 看用量；必要時 `npm run cleanup:logs -- --apply` |
| 每學年 | 跑一次金鑰輪替（見 `docs/金鑰輪替.md`） |
